HTTP requests and responses

Every method is there, including QUERY, HEAD, OPTIONS and custom ones. Query parameters, path parameters and headers are tables whose rows you can switch off one by one, or edit as plain text. A body is JSON, XML, HTML, YAML or plain text, a URL-encoded or multipart form, or a file, and JSON bodies can be checked, formatted and minified.

Each request can set its own timeout, whether to follow redirects, TLS verification, the HTTP version and how the URL is encoded. The request on the wire is the one you wrote: the few headers PostSonde adds are listed in a preview, and each can be turned off.

The response pane shows the status, time and size, the body pretty-printed or raw and filtered with JSONPath or XPath, the headers, the cookies, and the results of the request's tests. Its timeline lists every hop, redirects included, with a waterfall of DNS, connect, TLS, waiting and download times, the TLS version and certificate chain, and the request exactly as it was sent. Large bodies stream to disk instead of memory, and any body can be saved to a file.

Earlier responses stay one click away. A response can be saved with the request as an example, compared side by side with another, or turned into a mock server route. A request can also be sent again and again, a set number of times or at an interval, with every result listed.

GraphQL

The schema comes from introspection, cached for when the server is unreachable, or from an SDL file in the project. The editor checks the query against it as you type and completes fields, arguments, variables, directives and enum values. Fill fields writes out the missing fields of a selection, to the depth you choose. A docs explorer browses the types, and the schema can be saved as SDL.

Queries and mutations go over HTTP, as POST or GET. Subscriptions use graphql-transport-ws, the older subscriptions-transport-ws, or GraphQL over SSE, and any operation can be sent over a WebSocket instead. File uploads follow the GraphQL multipart request spec, and a response that uses @defer or @stream shows each part as it arrives.

gRPC

PostSonde reads .proto files itself, imports and include paths included, so you don't need protoc. The services can also come from server reflection, and they are cached, so the editor still knows them when the server is down.

Unary, server-streaming, client-streaming and bidirectional calls are supported, with metadata, a deadline and TLS. Messages are written as JSON, with completion from the message types. A call's log lists the messages in both directions with the headers, the trailers and the final status, and the error details in a status are decoded.

WebSocket, Socket.IO, SSE, TCP and UDP

A WebSocket request has its subprotocols and headers, sends text, or binary typed as hex or Base64 or loaded from a file, and keeps saved messages to send again. The log shows both directions, binary as a hex dump.

Socket.IO talks to v3 and v4 servers, and to v2 servers with a switch, over WebSocket or long-polling. It emits events, listens for them and handles acknowledgements.

Server-Sent Events appear as they arrive, and a stream can reconnect on its own and carry on from the last event ID.

Raw TCP connections can use TLS and split messages by line or by a length prefix, and input can be typed as text or hex. UDP sends datagrams directly or through a SOCKS5 proxy.

Tests work on streams as well: on any message, every one, none, the first, the last or a given one, or on the number of messages.

Local servers

PostSonde can run servers for the clients you are working on:

  • a mock HTTP server, whose routes you write by hand, generate from an OpenAPI document or make from a response you received, with templated responses;
  • an echo server, which answers each request with a JSON description of it;
  • a webhook receiver, which answers any request and keeps each one whole, to inspect and to send again;
  • WebSocket, Socket.IO, SSE, TCP and UDP servers;
  • gRPC and GraphQL mock servers.

They listen on 127.0.0.1 unless you choose another address, can use TLS, and log every connection and message. A folder can keep a server's settings in its _folder.json, so the server travels with the project.

Auth

Basic, bearer tokens, API keys in a header or the query, Digest (MD5, SHA-256 and SHA-512-256), JWTs signed at send time with HMAC, RSA, ECDSA or EdDSA keys, OAuth 1.0, AWS Signature Version 4, Hawk, and the credentials of a .netrc file.

OAuth 2.0 covers client credentials, the authorization code grant with PKCE (you sign in through your own browser, which hands the code back to a loopback port), the password grant and the implicit grant. Tokens are kept on your computer and refreshed when they expire, and the OpenID Connect ID token can be sent in place of the access token.

A request can inherit the auth of its folder, and WebSocket, Socket.IO and gRPC handshakes carry the same auth. Client certificates for mutual TLS, as PEM files or PKCS#12, are set per host.

Environments, variables and secrets

Variables come from the active environment, the project's global variables, the collection and each folder, and from the values that extraction rules take from responses. {{name}} works in URLs, headers, bodies, auth fields and more, and the editors mark a name that doesn't resolve. Dynamic values such as {{$uuid}}, {{$timestamp}} or {{$randomInt}} are filled in when the request is sent, and {{$response …}} reads from another request's last response.

Secret variables are kept out of the project folder, and so are local values, which replace a shared value on your computer only. Once you set a master password, the secrets on disk are encrypted with AES-256-GCM. The key can also go into the system keychain, so you don't have to type the password at every start.

Tests and the folder runner

A test is a row of target, operator and expected value. The target is the status, a header, a cookie, a JSONPath or XPath result, a regular expression, the body, the time or the size. A JSON Schema check validates a body, or part of it, against a schema. There is no scripting, and the tests run after every send.

Extraction rules take a value from a response, such as a token or a new ID, and put it in a variable for the requests that follow.

The folder runner sends a folder's requests in order, or the ones you pick in the order you pick. It runs them a number of times or once per row of a CSV or JSON file, with a delay between requests if you want one, and can stop at the first failure. Past runs are kept, and a run can be saved as a JUnit XML, JSON or HTML report.

Import, export and code

Import reads cURL commands, Postman collections, environments and globals, Insomnia v4 and v5 exports, OpenAPI 3.0 and 3.1 and Swagger 2.0 documents, HAR files and Altair exports. It shows what it will create before it writes anything, and reports what it had to leave out. A cURL command pasted into the URL field becomes a request.

Folders can be exported for Postman, as HAR, or as a zip of the project files, and environments can be exported on their own.

The Code tab writes a request out as a cURL command for a POSIX shell, cmd or PowerShell, as an HTTPie or wget command, as raw HTTP, or as code for JavaScript fetch, Python requests, Go net/http, Java HttpClient or C# HttpClient.

Proxies, certificates and cookies

Every connection goes through one dialer, so the proxy settings apply to every protocol: SOCKS5 and SOCKS5h with a user name and password, SOCKS4 and SOCKS4a, and HTTP or HTTPS proxies. By default PostSonde uses the system's proxy settings (on Linux, GNOME's settings or the proxy environment variables). A project or an environment can have a proxy of its own, and a bypass list sends some hosts direct.

Extra CA certificates and per-host client certificates apply to every TLS connection. Cookies are kept in a jar per project, or per environment if you prefer, and the cookie manager lists and edits them. The console's Connections view shows every connection the app has open.

Project files

A project is a folder with a postsonde.json at the top, one JSON file per request, a directory with a _folder.json for each folder, and one file per environment. The format is documented field by field and versioned. Changes made outside PostSonde, by an editor or a git pull, show up in the tree within a couple of seconds.

History, cookies, tokens and secret values stay in PostSonde's data directory instead, never in the project. Deleted requests go to a trash you can restore from, and scratch requests let you try something without adding it to the project.

The app

Light and dark themes follow the system or your choice, and a custom theme is a small JSON file. The command palette (Ctrl+Shift+P, or ⇧⌘P on a Mac) runs any action, Ctrl+P (⌘P) jumps to a request, folder or environment, and every shortcut can be changed.

A project can be open in several windows. The response sits beside the request or below it, and focus mode hides everything but the request and its response. Requests and folders can carry notes in Markdown.

The settings are one JSON file you can edit by hand, and an administrator can lock some of them with a policy file. In portable mode PostSonde keeps its settings and data in a folder next to the app. The interface is in English.
